# Заставка дисплея (splash)

Стартова заставка — монохромна битмапа **64×64** у `display.h`
(`static const unsigned char ngu_xbm[] = { ... };`, розмір `NGU_W`/`NGU_H`).

Для **кольорових TFT ST7789** — окремий генератор кольорової заставки нижче.

## Замінити на своє зображення (монохромні дисплеї)

Використайте **своє** зображення (на яке маєте права):

```bash
pip install pillow
python tools/make_splash.py моя_картинка.png            # темне -> світиться
python tools/make_splash.py моя_картинка.png --invert   # інверсія
python tools/make_splash.py моя_картинка.png --dither    # напівтони (дизеринг)
```

Скрипт надрукує готовий блок `#define NGU_W/H` + `ngu_xbm[]` — вставте його у
`display.h` замість наявного масиву. Розмір лишається 64×64.

> ⚠️ Не використовуйте захищені авторським правом персонажі/лого без прав на них.

## Кольорова заставка (TFT ST7789)

Для кольорових дисплеїв — `make_color_splash.py`: генерує `custom_splash.h`
з масивом **RGB565** під вашу роздільність.

```bash
pip install pillow
python tools/make_color_splash.py logo.png -W 240 -H 240     # ST7789VW 240x240
python tools/make_color_splash.py logo.png -W 240 -H 280     # ST7789V3 240x280
python tools/make_color_splash.py logo.png -W 240 -H 320 --fit cover
python tools/make_color_splash.py logo.png --bg 001B3A       # колір фону (HEX)
```

Покладіть згенерований `custom_splash.h` у папку скетчу і ввімкніть у
`settings.h`:  `#define DISPLAY_SPLASH_CUSTOM`. Заставка малюється по центру.

## Розбір і звірка дампів (`decode_dump.py`)

Анотований розбір дампа IMPRES-чіпа й побайтова звірка «еталон vs клон».
Перевіряє ті самі інваріанти, що й прошивка: заголовок DS2433 Σ≡0x41,
TLV-записи Σ≡0x5A, дзеркало DS2438[24:50]↔DS2433[1:27], ємність (запис 0x17+21),
ETM/ICA/CCA/DCA у DS2438.

```bash
# Розбір дампа (DS2438 — необов'язковий)
python tools/decode_dump.py dump33.bin dump38.bin

# Витягти вшитий еталон із templates.h у .bin (для звірки клонів)
python tools/decode_dump.py --template PMNN4409B --out ref
#   -> ref_33.bin (512) + ref_38.bin (64)

# Побайтова звірка: «●» — розбіжність в ідентичності/калібруванні (важливо),
#                   «○» — лічильники/живі виміри (норма після скидання)
python tools/decode_dump.py ref_33.bin ref_38.bin --diff clone33.bin clone38.bin
```

## Хостові тести (`*_check.cpp`)

Збираються звичайним `g++` і ганяються **на комп'ютері**, без ESP32. Запускати
з КОРЕНЯ проєкту — частина з них читає корпус дампів у `dumps/`:

```bash
mkdir -p build
for f in tools/*_check.cpp; do
  n=$(basename "$f" _check.cpp)
  g++ -std=c++17 -I. -Itools/fake -o "build/$n" "$f" && "./build/$n" || echo "ЗБІЙ: $n"
done
```

### ⚑ Матриця конфігурацій — одного прогону мало

Один код обслуговує **два пристрої** (`DEVICE_VARIANT`), а всередині того з
них, що має власний понижувач, є ще й **два силові ключі**
(`CHARGE_SWITCH_TYPE`). Обидва вибори міняють не оформлення, а самі числа й
самі гілки коду, тож зелений прогін в одній конфігурації нічого не доводить
про другу. Мінімальна чесна матриця — ТРИ прогони, плюс **четвертий: збірка
без Bluetooth**.

Четвертий доданий не для повноти. У ньому живе правило, якого в решті трьох
немає з чого перевірити: у файлі налаштувань записано «зв'язок через
Bluetooth», а підняти його нічим — прошивку перезібрали без стека. Прилад
мусить підняти Wi-Fi, а не мовчати в обох ефірах. Звірка «від протилежного»
це й показала: дві поломки в `radio_mode.h` не валили НІЧОГО у трьох
основних конфігураціях і валили свої перевірки лише тут.

```bash
mkdir -p build
for dev in 0 1; do                        # 0 = плата TL494, 1 = власний понижувач
  for sw in 0 1; do                       # тип ключа має сенс лише в понижувача
    [ "$dev" = 0 ] && [ "$sw" = 1 ] && continue
    for f in tools/*_check.cpp; do
      n=$(basename "$f" _check.cpp)
      g++ -std=c++17 -I. -Itools/fake \
          -DDEVICE_VARIANT=$dev -DCHARGE_SWITCH_TYPE=$sw \
          -o "build/$n" "$f" && "./build/$n" >/dev/null \
          || echo "ЗБІЙ: $n (пристрій $dev, ключ $sw)"
    done
  done
done
# ⚑ ЧЕТВЕРТИЙ ПРОГІН: збірка без стека Bluetooth. Див. пояснення вище.
for f in tools/*_check.cpp; do
  n=$(basename "$f" _check.cpp)
  g++ -std=c++17 -I. -Itools/fake -DBT_OFF -o "build/${n}_off" "$f" \
      && "./build/${n}_off" >/dev/null || echo "ЗБІЙ БЕЗ BT: $n"
done
python3 tools/topology_check.py          # чужі імена в живому коді — обидві топології
python3 tools/check_page_js.py           # цілісність вшитої сторінки
python3 tools/client_audit.py            # обробники й кнопки в усіх трьох клієнтах
python3 tools/templates_reply_check.py   # список моделей у клієнті-програмі
```

`tools/topology_check.py` стоїть окремо не для симетрії: `web_server.h` на
хості **не збирається взагалі**, тож жоден `*_check.cpp` не побачив би там
звертання до макроса, якого за обраної топології не існує. Препроцесувати
його при цьому цілком можна — на цьому перевірка й побудована (докладніше — у
шапці самого файлу). Вона ганяє саме `CHARGE_TOPOLOGY`, а не `DEVICE_VARIANT`:
питання там суто про заряд, і прив'язувати його до екрана не було б за що.

І, окремо, **панель операції повертається в початковий стан**: JSON віддає ДВА різні поля («яким показати підсумок» і «чи зайняте залізо») з різних функцій прошивки; клієнти ховають уставки за другим, а не за першим; кінцеві точки «прибрати підсумок» існують, підключені й НЕ закриті гейтом вимкненого заряду; усі три клієнти мають і дію, і кнопку, і видимий показ недоступності. Перевіряються **визначення** функцій, а не згадки імені: кнопка з `onclick` лишає ім'я у файлі й тоді, коли функції вже немає |

> проєкті вже був випадок, коли `chargeMarkDirty()` працював бездоганно, а
> `chargeConsumeDirty()` у скетчі не викликав ніхто, і заряд ніколи не оновлював

| `wizard_check` | **правила Майстра відновлення** на справжньому `wizard_rules.h` (заради цього тесту чисту частину правил і винесено з `recovery.h`, який на хості не збирається): перелік проблем суцільний і без дірок; кожна проблема має і діагноз, і пропозицію; кожна потрапляє **або** в план робіт, **або** в перелік «кроку не буде — ось чому» (і «ні там, ні там», і «і там, і там» валять тест — саме так знайшлися п'ять проблем, які Майстер називав і мовчки лишав без ліків); кожен крок має назву, опис і **власний** машинний код; крок, що пише в чип, називає який; порядок плану — ремонт структури перед перешифруванням, станція після калібрування, правка лічильника **не** перед скиданням, яке її зітре, перевірка результату завжди остання, «чіпів немає» обриває план на читанні |
| `templates_reply_check` | **список моделей-еталонів у клієнті-програмі** (`usb_client/moto_models.py`): невдала відповідь на `TEMPLATES` не сміє затирати вже завантажений список; порожнеча ніколи не мовчить, а два її різні випадки («не приїхало» проти «у прошивці немає шаблонів») не плутаються, бо поради в них протилежні; напис-заглушку неможливо ВИБРАТИ й неможливо відправити в запис; і, окремо, що всі три поверхні (Майстер, «Новий акумулятор», «Відновити еталон») питають ОДНУ перевірку готовності, у Майстрі є кнопка «оновити список», а сам `TEMPLATES` більше не питається першим у пачці команд під'єднання |
| `radio_mode_check` | **режим зв'язку** на справжньому `radio_mode.h`: увімкнених радіо рівно одне на КОЖНОМУ з 256 значень (число приходить із файла, який могли побити, і з команди ззовні); те, що не підняти, не обирається — і в збірці з Bluetooth, і в збірці без нього (доступність передається параметром, а не читається з `#ifdef`, інакше половина правил перевірялась би лише в одному світі); коло режимів не заводить у недоступний і не просить перезавантаження дарма; файл налаштувань пишеться, читається й **розуміє старий формат** (у приладі власника в ньому записано, що силової частини немає); розбір каже, ЩО ЗАПИСАНО, і не вирішує за залізо — на це є окреме правило, і саме воно рятує від німого приладу |
| `buzzer_dac_check` / `buzzer_ledc_check` | синтез звуку (ЦАП і ШІМ); вмикають звук ЯВНО, незалежно від того, який вихід обрано в `settings.h` — тест на ШІМ мусить проходити й тоді, коли в пристрої стоїть ЦАП; побічно пишуть демо-`.wav` у поточну теку |

Кожен тест друкує підсумковий рядок і повертає ненульовий код при збої.

## Допоміжні скрипти

| Скрипт | Навіщо |
|---|---|
| `mk_page_header.py` | вшиває `index.html` у прошивку: робить `page_index.h` (gzip). **Запускати після кожної правки сторінки** — охоронець 27 звіряє їх за CRC32 і сам друкує цю команду |
| `check_page_js.py` | синтаксична перевірка всього вбудованого JavaScript (обидві сторінки й аварійна `PAGE_LITE`). Помилка в скрипті дає білий екран у браузері, і без цієї перевірки знайти її можна лише на пристрої. Потребує `node`; без нього чесно каже, що нічого не перевіряв |
| `client_audit.py` | аудит клієнтів: кожен `onclick` має існуючу функцію, кожен `$('id')` — елемент, кожен викликаний API/USB-командa є в прошивці; ключ шифрування береться з ROM цільового чипа. **Плюс єдиний вигляд панелей операцій**: склад і порядок плиток заряду / розряду / пробудження звіряються **між трьома клієнтами** (уміє розібрати і JS, і Python) — порядок порівнюється списком, бо однаковий набір у різному порядку і є «різні панелі»; кожна плитка мусить десь заповнюватись; панелі мусять малюватись спільним кодом (`opTiles`/`opBand`/`opSpark` у вебі, один клас `OpMonitor` в `.exe`) |
